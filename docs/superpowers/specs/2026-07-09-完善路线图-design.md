## 1. 背景与目标

被测系统是制造业 MES + WMS 一体化平台。本仓库 AutoTest Studio 是面向测试人员的自动化测试管理平台：把 Playwright 脚本包装成「场景 + 样本数据 + 执行 + 报告」工作流，减轻手工录入与重复操作。

**核心痛点：**

1. 测试数据准备繁琐
2. 界面功能操作重复
3. 场景多、管理难

**完善总目标：** 在现有平台骨架上，按可演示价值分阶段补齐场景覆盖、可维护性与智能化，最终形成测试人员可自助使用的回归平台。

- 每阶段必须可独立验收、可演示

## 5. P1：高优场景扩展

### 5.1 目标

补齐 `AGENTS.md` 中仍缺的高优先级业务场景，替代更多手工录入。

### 5.2 新增场景清单

| 顺序 | 场景 key | 模块 | 依赖 | 说明 |
|------|----------|------|------|------|
| 1 | `wms-locator-create` | WMS / ImsLocator | 仓库主数据已存在 | 库位维护 |
| 2 | `wms-po-create` | WMS / ImsPoMst | 供应商 + 物料 | 采购订单创建 |
| 3 | `wms-so-create` | WMS / ImsSoMst | 客户 + 物料 | 销售订单创建 |
| 4 | `base-excel-import` | 基座 / ImportExcel | 导入模板配置 | Excel 批量导入 |
| 5（可选） | `base-user-manage` | 基座 / User | 组织/角色 | 用户管理 CRUD |

### 5.3 每个场景的交付物

1. `server/platform/seed.mjs` 增加场景定义 + `dataSchema`
2. Playwright spec（新建或扩展现有 `wms-*.spec.js` / 基座 spec）
3. `docs/sample-data/<key>.csv` 样例
4. 平台单测：场景出现在 catalog、模板可下载、数据集可校验

### 5.4 关键约束

- **依赖数据：** P1 先用「样本数据写死已有编号」或「执行前检查并跳过」；正式依赖链留给 P2
- **定位策略：** 继续复用 `tests/support/autotest-ui.js`
- **不做：** 场景录制、AI 生成、场景 UI 编辑

### 5.5 验收

- [ ] 平台场景库可见上述 4 个新场景（用户管理可选）
- [ ] 每个场景：下载模板 → 上传样例 → 执行 → 报告可查看
- [ ] 真实环境至少跑通库位 + 采购（或销售）各 1 次成功
- [ ] `npm test` 保持全绿

## 6. P2：平台可扩展性

### 6.1 目标

新场景不必只靠改代码种子入库；支持场景组合与多环境。

### 6.2 能力清单

| 能力 | 做什么 |
|------|--------|
| 场景 CRUD | 维护员/管理员可在 UI 新建、编辑、发布/下架场景（key、模块、scriptEntry、dataSchema） |
| 场景依赖链 | 场景声明 `dependsOn`；执行前自动跑前置或校验前置数据就绪 |
| 多环境配置 | 管理 `baseUrl` / 账号；执行时可选环境 |
| 精确执行 | Runner 按 `scriptEntry` 只跑目标 spec |
| 发布入口 | 前端暴露已有 `publish` API |

### 6.3 数据与接口要点

- SQLite：`scenarios.depends_on`；`environments` 表（或 settings 存环境列表）
- API：`POST/PUT /api/scenarios`、`GET/POST /api/environments`；创建执行时带 `environmentId` 并解析依赖
- UI：场景详情可编辑（maintainer+）；执行弹窗增加环境选择与依赖提示

### 6.4 涉及文件（预期）

- `server/platform/database.mjs`
- `server/app.mjs`
- `server/platform/runner.mjs`
- `web/app.js`
- `tests/platform/*.test.mjs`

### 6.5 验收

- [ ] 维护员可新建草稿场景并发布；测试员只能执行已发布场景
- [ ] 声明依赖的场景执行时展示依赖状态；缺失时给出明确失败原因
- [ ] 至少配置 2 个环境并可切换执行
- [ ] Runner 按 `scriptEntry` 精确调用 Playwright
- [ ] 单测覆盖 CRUD / 依赖解析 / 环境选择

### 6.6 不做

- Codegen 录制入库
- AI 数据生成 / 自愈
- 定时任务、批量并行调度

## 7. P3：智能化

### 7.1 目标

降低数据准备成本，提升脚本抗 UI 变更能力，补齐场景脚本录制。

### 7.2 能力清单

| 能力 | 做什么 | 边界 |
|------|--------|------|
| AI 测试数据生成 | 按 `dataSchema` + 业务约束调用 LLM 生成样本 | 失败回退规则引擎 |
| 自愈定位器（基础版） | 失败时候选链：label → placeholder → 邻近文本 → 角色/按钮 pattern | 不做视觉大模型定位 |
| 场景录制入库 | Playwright Codegen → 草稿 spec + 建议 schema → 人工审核发布 | 不自动上线 |
| LLM 配置可用 | 连通性测试 + 生成数据入口 | API Key 掩码存储 |

### 7.3 落地顺序

1. AI 数据生成
2. 自愈定位器基础版
3. 录制入库（依赖 P2 场景 CRUD）

### 7.4 验收

- [ ] 场景详情可「AI 生成 N 行数据」，校验通过后可直接执行
- [ ] LLM 不可用时回退规则生成并提示原因
- [ ] 至少 1 个真实定位失败用例能被候选链自愈并写入过程日志
- [ ] 维护员可启动录制 → 草稿场景 → 编辑后发布
- [ ] 单测覆盖 AI 回退、heal 候选链、录制草稿创建（mock）

### 7.5 不做

- 无人工审核的脚本自动上线
- 基于截图的视觉大模型定位
- 跨项目通用测试平台产品化

## 8. 风险与依赖

| 风险 | 影响 | 缓解 |
|------|------|------|
| 测试环境不稳定 / 数据被污染 | P0/P1 冒烟失败 | 使用带前缀的自动化编号；失败时保留过程证据 |
| 微前端 / Element UI 定位脆弱 | 场景扩展成本高 | P0 先加固 `autotest-ui.js`；P3 再上自愈 |
| 采购/销售依赖主数据 | P1 场景偶发失败 | P1 用固定样例编号；P2 上依赖链 |
| LLM 不可用或密钥缺失 | AI 生成不可用 | 强制规则回退，不阻塞执行链路 |
| 录制脚本质量参差 | 误发布不稳定场景 | 强制人工审核 + 草稿状态 |
